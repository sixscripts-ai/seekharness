SeekHarness backend: what actually executes

Code-grounded map of the package supplied on Aug 19, 2026. The central mental model is Format config → executor selection → agent loop → ToolSession → OS subprocess → evidence callbacks. A format is not itself an execution script.

Which component does what?

seed_formats.py
Challenge manifest. Defines the game. It should say what agents must do, not implement shell behavior.
executors/__init__.py
Router/factory. Maps a format or engine to the correct executor class.
advanced_executor.py
General agent runtime. Prompt → model output → parse TOOL calls → execute → evidence → iterate.
ToolSession
Tool API. read/write/ls/run/test/shell/install/fetch/bg/ps/kill/logs/use_skill. This is the agent's effective operating system API.
procs.py
Background process manager. Writes commands to .arena_bg/<name>.sh, starts them in a process group, keeps ring-buffered stdout/stderr, kills process groups.
sandbox_launcher.py
Isolation/bootstrap. Starts Modal, creates battle-scoped credentials, decides real sandbox vs local fallback behavior.
internal_router.py
Trusted broker. Sandbox calls backend for model/judge/finalize operations without receiving provider/Appwrite secrets.
event_bus.py + LiveBattle.tsx
Observability/UI. Shows event data. It is not itself the terminal runtime.

Current quality assessment

GOOD · Clear separation between trusted backend and untrusted sandbox; battle-scoped sandbox token is the right direction.
GOOD · ToolSession has path-jail checks, symlink defense, process-group termination, output caps, step budgets, timeouts, and SSRF checks for its dedicated fetch tool.
GOOD · Format config is mostly separated from execution mechanics, which makes Arena extensible.
LIMIT · There is no real PTY terminal in this package. Shell calls are discrete subprocess executions and background jobs. No stdin stream, terminal resize, PTY ownership, or human/agent input arbitration appears in the code.
LIMIT · The model emits a custom text protocol (TOOL shell ...) parsed by regex/string logic. It works, but is more fragile than schema-native tool/function calling.
LIMIT · “action_log” is evidence after a tool action; it is not a command lifecycle journal with queued/authorized/started/output/exited/committed states.
ENHANCE · For a true live cloud-terminal agent console, introduce a dedicated Execution Session / PTY service and make AdvancedExecutor a planner/orchestrator over that service rather than the process owner itself.

Example: what happens when an agent runs a command?

User selects “Code review duel”
  → format config says universal=True, target_code, test_code, max_tool_steps=14
  → runner.get_executor(config)
  → AdvancedExecutor.run_battle(...)
  → model receives prompt listing TOOL shell / TOOL run / TOOL test / etc.
  → model replies: TOOL shell cmd='pytest -q'
  → parse_tool_calls(...) creates { tool: "shell", cmd: "pytest -q" }
  → ToolSession.exec_tool(...)
  → ToolSession.shell(...)
  → subprocess.Popen(["bash", "-c", "pytest -q"], cwd=workdir, start_new_session=True)
  → stdout/stderr/rc returned as text
  → AdvancedExecutor emits event_type="action_log"
  → result is also recorded as an artifact
  → sandbox client POSTs callback to /internal/*
  → backend event_bus persists/publishes
  → LiveBattle SSE renders TOOL / ARTIFACT activity
  → model receives another turn and decides the next tool action
Key design conclusion: your current Arena already has a credible agent tool harness. The next architectural leap is not “more formats.” It is to promote execution into its own durable session subsystem: PTY/process identity, structured command lifecycle, capability/policy checks before execution, streaming stdout/stderr, durable evidence sequencing, reconnect/resume, and explicit human-vs-agent terminal ownership.
